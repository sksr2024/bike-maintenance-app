# 0011 フロント未実装でも認証APIの結合テストが書ける理由

## 疑問の出発点

[[0010-認証tokenの保持とAuthorizationヘッダーの付与は誰の仕事か]] で見た通り、tokenの保存とAuthorizationヘッダーへの付与はフロントエンド側のコードが自前で書く必要がある。ところが `frontend/src/` にはまだその実装がない。それなのに `backend/test/integration/auth.test.ts` には `GET /auth/me` や `POST /auth/logout` が正しく動くことを検証するテストが既に存在し、パスしている。フロントが無いのにどうやってtokenを「保持」して次のリクエストに使っているのか、という疑問。

## 答え：テストがブラウザの代わりにtokenを運んでいる

`auth.test.ts:6-14` のヘルパー関数を見るとわかる。

```ts
async function signupAndLogin(app: ReturnType<typeof createApp>): Promise<string> {
  await request(app)
    .post('/auth/signup')
    .send({ email: 'rider@example.com', password: 'correct-horse' });
  const loginResponse = await request(app)
    .post('/auth/login')
    .send({ email: 'rider@example.com', password: 'correct-horse' });
  return loginResponse.body.token as string;
}
```

このテストは `supertest` というライブラリを使い、`createApp()`（`backend/src/app.ts`）が返すExpressアプリに**直接**リクエストを送っている。ブラウザもfetchもlocalStorageも一切登場しない。ログインのレスポンスボディからtokenを取り出して `return` しているだけで、これは本来ブラウザの `localStorage.setItem()` が担うはずの「保存」を、**テストコードのローカル変数**が代わりに肩代わりしているに過ぎない。

その後、`/auth/me` や `/auth/logout` を呼ぶ箇所（`auth.test.ts:108`, `142`）で、その変数を使って明示的にヘッダーを組み立てている。

```ts
const response = await request(app).get('/auth/me').set('Authorization', `Bearer ${token}`);
```

`.set('Authorization', ...)` が、本来フロントエンドのfetchラッパーやaxiosインターセプターが担うはずの「ヘッダー付与」の代役になっている。

## なぜこれで意味のあるテストになるのか

このテストが検証しているのは「フロントエンドが正しく動くか」ではなく、**バックエンドAPIの契約（インターフェース）が正しいか**という別の問いだからだ。

- 正しいtokenを `Authorization: Bearer <token>` で渡せば `200` を返すか（`auth.test.ts:104-112`）
- ヘッダーが無ければ `401` を返すか（`114-120`）
- 存在しないtokenなら `401` を返すか（`122-128`）
- ログアウト後は同じtokenがもう使えなくなるか（`136-147`）

これらはすべて「サーバーが受け取ったHTTPリクエストにどう応答するか」の話であり、そのリクエストをブラウザが組み立てようが、テストコードが組み立てようが、Expressのルーター（`backend/src/routes/auth.ts`）や `requireAuth` ミドルウェア（`backend/src/auth/middleware.ts`）にとっては区別がつかない。むしろフロントエンドを介さず直接HTTPレベルでテストすることで、フロントエンドの実装バグとバックエンドの実装バグを切り分けられるという利点がある。

## この先に必要になるテストの種類

フロントエンドを実装した後は、今回のような「サーバーの契約を検証するテスト」とは別に、「ブラウザ上でログインしたら本当にlocalStorageにtokenが保存され、次のページ遷移後のAPIリクエストにも自動でヘッダーが付くか」を検証するテストが別途必要になる。これは `backend/test/integration/` のような結合テストではなく、フロントエンド側の結合テストやE2Eテスト（例: Playwrightでブラウザを実際に操作するテスト）が担う領域になる。バックエンドの結合テストが緑色でも、フロントエンドのtoken管理コードにバグがあれば実際のアプリは壊れうる、という点は覚えておく必要がある。

## 使われている技術と、それぞれの役割

このテストを動かすために3つの技術が組み合わさっている。それぞれ役割が違うので、どれが何を担当しているかを分けて理解すると全体像がつかみやすい。

| 技術 | 役割 | このプロジェクトでの設定場所 |
|---|---|---|
| **Vitest** | テストランナー（テストを発見して実行し、成功/失敗を報告する） | `backend/vitest.config.ts`, `package.json` の `scripts.test` |
| **supertest** | HTTPリクエストを組み立ててExpressアプリに送るライブラリ | `auth.test.ts` 内で `request(app)` として使用 |
| **node-pg-migrate** | テスト用DBにテーブルを作るマイグレーションツール | `backend/test/globalSetup.ts` |

### 1. Vitest — テストの土台

`backend/package.json` の `scripts` を見ると、テストの実行コマンドはこうなっている。

```json
"test": "dotenv -e .env.test -- vitest run",
```

`vitest run` がVitest本体の起動コマンドで、`describe` や `it`、`expect` といった `auth.test.ts` 内で使われている関数はすべてVitestが提供している。`dotenv -e .env.test --` は「`.env.test` に書かれた環境変数（テスト用DBの接続先など）を読み込んでから実行する」という前置き部分。

Vitestは `backend/vitest.config.ts` の設定に従って、テスト実行前に一度だけ `globalSetup` を走らせる。

```ts
export default defineConfig({
  test: {
    globalSetup: './test/globalSetup.ts',
  },
});
```

`test/globalSetup.ts` の中身は `node-pg-migrate` を使ってテスト用DBに最新のマイグレーション（`users`テーブルや`sessions`テーブルの作成など）を適用する処理。これにより、テストは「実際に動くPostgreSQLのテーブル構造」に対して実行される。モック（偽物のDB）ではなく本物のDBを使う結合テストになっているのがポイント。

### 2. supertest — ブラウザなしでHTTPリクエストを送る

`auth.test.ts` の先頭にある

```ts
import request from 'supertest';
import { createApp } from '../../src/app.js';
```

がこのテストの核。`createApp()`（`backend/src/app.ts:5-20`）は、ミドルウェアやルーターを登録したExpressアプリのインスタンスを**サーバーとして起動せずに**返す関数。supertestはこのアプリインスタンスを直接受け取り、

```ts
const response = await request(app)
  .post('/auth/signup')
  .send({ email: 'rider@example.com', password: 'correct-horse' });
```

のように「実際にHTTPサーバーをポートで待ち受けさせなくても、内部的にリクエスト/レスポンスのやり取りを再現してくれる」。これにより `npm run dev` でサーバーを立ち上げたり、`curl` を手打ちしたりせずに、コードの中だけで「POSTリクエストを送って、返ってきたstatusとbodyを検証する」という一連の流れをテストできる。

### 3. TDDでの実装の流れ

このテストはTDD（テスト駆動開発）で書かれたため、実装コード（`auth.ts`, `middleware.ts`, `session.ts`）より先にテストコードが存在した時期がある。流れを追うとこうなる。

1. **Red**: `POST /auth/login` や `GET /auth/me` のルートがまだ存在しない状態で `auth.test.ts` を書く。この時点で `npm test` を実行すると、ルートが無いため `404` が返り、`expect(response.status).toBe(200)` などのアサーションが失敗する（赤）。
2. **Green**: 失敗を解消する最小限の実装を `backend/src/routes/auth.ts` や `backend/src/auth/middleware.ts` に追加する。たとえば最初は `POST /auth/login` のルートハンドラを書き、`res.status(200).json({ token })` を返すところまで実装してテストを通す。
3. **Refactor**: テストが通った状態を保ちながら、`extractBearerToken` を `session.ts` に切り出す、パスワードハッシュ化を `password.ts` に分離するといった整理を行う。

`signupAndLogin` ヘルパー（`auth.test.ts:6-14`）がまさにこの過程で生まれたコード。`GET /auth/me` や `POST /auth/logout` のテストを書く際、毎回「signupしてloginしてtokenを取り出す」という同じ手順を繰り返す必要があったため、共通化された。

### 4. 実際にテストを実行するコマンド

```bash
cd backend
npm test
```

これを実行すると、`.env.test` の内容（テスト専用DBの接続情報）が読み込まれ、`globalSetup.ts` がテスト用DBにマイグレーションを適用し、その後Vitestが `test/integration/*.test.ts` に一致するファイルをすべて実行する。各 `describe` ブロックの `beforeEach` で `resetDb()`（`backend/test/helpers/resetDb.ts`）が呼ばれ、`TRUNCATE TABLE sessions, users RESTART IDENTITY CASCADE` でテーブルを空にしてからテストを行う。これにより、あるテストで作ったユーザーが別のテストに影響を与えないよう、テストごとにDBの状態がリセットされた状態から始まる。

### まとめると

- **本物のPostgreSQL**（`node-pg-migrate` でマイグレーション済み）に対して
- **本物のExpressアプリ**（`supertest` 経由、ただしポートは開かない）に
- **Vitest** がテストケースを順に実行し
- 各テストは `beforeEach` でDBをリセットしてから独立して走る

という構成になっている。フロントエンドが未実装でも、「本物のブラウザ」の代わりに「supertestが組み立てたHTTPリクエスト」と「テストコードのローカル変数」が代役を務めることで、API単体の正しさを保証できている。
