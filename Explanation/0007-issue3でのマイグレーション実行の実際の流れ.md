# issue #3でのマイグレーション実行の実際の流れ

[0004](0004-PostgreSQLとマイグレーションの仕組み.md)ではnode-pg-migrateの一般的な仕組みを説明したが、ここではissue #3の実装セッションで**実際に何を実行したか**を時系列で記録する。node-pg-migrateの標準的な使い方（`create`で雛形生成→編集→`up`で適用→必要なら`down`で巻き戻し）と比べると、このセッションでは①の自動生成ステップを省略している点、③の「適用」が開発用DBとテスト用DBで異なる経路をたどる点の2つが実態として異なる。

## ①`node-pg-migrate create`は使っていない

標準的な使い方では`npx node-pg-migrate create <name>`でタイムスタンプ付きの雛形ファイルが自動生成される。今回はこのコマンドを一度も実行していない。代わりに、issue #2で既に存在していた雛形マイグレーション`backend/migrations/1786024913011_bootstrap-schema.js`と同じ構造（`shorthands`のエクスポート、`up`/`down`のJSDocコメント）をそのまま踏襲し、ファイルをゼロから直接書いた。

ファイル名先頭のタイムスタンプも、node-pg-migrateに生成させる代わりに手で用意した。

```sh
node -e "console.log(Date.now())"
# => 1787647367781
```

この数値をそのままファイル名`1787647367781_create-users-and-sessions.js`に使っている。つまり、標準的な流れの①（自動生成）が、②（手書き）の作業に統合された形になっている。

## ②`up`/`down`を手書き

[0006](0006-issue3認証機能の実装詳細.md)で解説した通り、`up`で`users`・`sessions`の2テーブルを`pgm.createTable(...)`で作成し、`down`でその逆順（`sessions`→`users`。外部キー制約のため子テーブルから先に消す必要がある）に`pgm.dropTable(...)`する処理を書いた。この時点ではまだファイルの中身がコードとして存在するだけで、DBには何も反映されていない。

## ③DBへの適用 — 開発用とテスト用で経路が違う

ここが一般的なnode-pg-migrateの解説には出てこない、このプロジェクト固有の分岐点。

### 経路A: 開発用DB（ポート5432）— CLIを手動実行

```sh
cd backend
npm run migrate           # => 引数(up/down)必須のためエラー、使い方ヘルプが表示された
npm run migrate -- up     # => 成功
```

`backend/package.json`のスクリプト定義。

```json
"migrate": "dotenv -e .env -- node-pg-migrate",
```

これは`node-pg-migrate`本体をdirection引数なしで起動するようになっており、`up`か`down`を明示的に渡す必要がある。最初`npm run migrate`とだけ実行したところ、node-pg-migrateの使い方（Usage）ヘルプが出力されてしまい、何も実行されなかった。`npm run migrate -- up`（`--`以降がそのままnode-pg-migrateへの引数として渡る）と実行し直して初めて、以下のようにSQLが実行され、開発用DBに反映された。

```
> Migrating files:
> - 1787647367781_create-users-and-sessions
CREATE TABLE "users" ( ... );
CREATE TABLE "sessions" ( ... );
INSERT INTO "public"."pgmigrations" (name, run_on) VALUES ('1787647367781_create-users-and-sessions', NOW());
Migrations complete!
```

### 経路B: テスト用DB（ポート5433）— CLIではなくプログラムAPIを直接呼び出し

[backend/test/globalSetup.ts](../backend/test/globalSetup.ts)は、CLIコマンドを一切経由せず、`node-pg-migrate`パッケージが公開しているJavaScript関数`runner()`を直接importして呼び出している。

```ts
import { runner } from 'node-pg-migrate';

export default async function setup() {
  await runner({
    databaseUrl: process.env.DATABASE_URL!,
    dir: 'migrations',
    direction: 'up',
    migrationsTable: 'pgmigrations',
    logger: { info: () => {}, warn: console.warn, error: console.error },
  });
}
```

vitestの`globalSetup`はテストファイル本体が実行される前に一度だけ呼ばれる仕組み（[vitest.config.ts](../backend/vitest.config.ts)の`test.globalSetup`で指定）なので、`npm test`を実行するたびに、この`runner()`呼び出しが自動的に走り、テスト用DB（`.env.test`の`DATABASE_URL`が指す5433番ポート）に未適用のマイグレーションを適用してからテストが始まる。人間が`npm run migrate:test -- up`を手で叩く必要はない。

つまり同じ「マイグレーションの適用」でも、開発用DBは人間がCLIコマンドを手動で叩く経路、テスト用DBはコードから関数として直接呼ばれる経路という、実行のされ方そのものが異なる2系統になっている。

## ④`down`は今回未使用

このセッションでは一度も`npm run migrate -- down`のようなロールバック操作を行っていない。テーブル設計をやり直したくなった場合も、直近のマイグレーションを巻き戻すのではなく、新しい差分を表す別のマイグレーションファイルを追加していくのが通常の運用になる（`down`は主にローカルでの試行錯誤や、直前に自分が適用したばかりの変更を取り消したい場合に使う）。

## まとめ

| 段階 | 一般的な流れ | 今回の実際 |
|---|---|---|
| ①雛形生成 | `node-pg-migrate create` | 実行せず。既存ファイルを手本に手書きで代替 |
| ②up/down記述 | 手動で編集 | 手動で記述（想定通り） |
| ③DB適用 | `node-pg-migrate up` | 開発用DB: CLI手動実行（`npm run migrate -- up`）／テスト用DB: `globalSetup.ts`から`runner()`関数を自動呼び出し |
| ④巻き戻し | `node-pg-migrate down` | 未使用 |
