# issue #4「整備記録の登録・一覧閲覧」の実装詳細

## 何を作ったか

[issue #4](https://github.com/sksr2024/bike-maintenance-app/issues/4)の要件は、ログイン中ユーザーが整備記録を登録する`POST /maintenance-records`と、実施日の新しい順で一覧取得する`GET /maintenance-records`の2エンドポイント。バリデーション・認可・空状態を含め、実HTTPリクエスト・実DBに対する統合テストで検証することがacceptance criteriaに明記されている。

## スコープの判断: バックエンドAPIのみを実装した理由

issueの本文には「一覧の各行で整備種別・実施日・走行距離・費用が確認できる」「記録が1件もない場合、空状態が表示される」という、一見フロントエンドのUI要件に見える記述がある。しかし今回はバックエンドAPIのみを実装し、フロントエンドの画面は作っていない。根拠は3つ。

1. 親issue [#1](https://github.com/sksr2024/bike-maintenance-app/issues/1)の「Testing Decisions」に「フロントエンドのコンポーネント単体テストは今回は設けない（フロントエンドは薄いAPI消費者として扱う）」「テストは『バックエンドAPI層』を唯一のシームとする」と明記されている。
2. 直前のissue #3（サインアップ・ログイン・ログアウト）も、[HANDOFF.md](../HANDOFF.md)の記録の通りバックエンドAPIのみで実装・クローズされており、[frontend/src/App.tsx](../frontend/src/App.tsx)には認証UIが一切存在しない（`/health`疎通確認のみ）。ログイン画面がない以上、その先の整備記録一覧画面だけを単独で作ることはできない。
3. issue #4自体の本文にも、フロントエンドのファイルパスやコンポーネントへの言及は一切ない。「一覧の各行で確認できる」「空状態が表示される」は、UIが実装された時にAPIレスポンスがその表示を成立させられることを指していると解釈した（一覧が空配列を返せば空状態を表示でき、必要なフィールドがレスポンスに揃っていれば各行を表示できる）。

そのため今回は、GETが空配列を返すこと・各行に必要なフィールドが揃っていることをAPIレベルの統合テストで検証する形にとどめている。フロントエンドの認証UI・整備記録UIは今後の別issueのスコープになる想定。

## データベース設計

新しいマイグレーション[backend/migrations/1788000000000_create-maintenance-records.js](../backend/migrations/1788000000000_create-maintenance-records.js)で`maintenance_records`テーブルを作成した。

```js
pgm.createTable('maintenance_records', {
  id: 'id',
  user_id: { type: 'integer', notNull: true, references: 'users', onDelete: 'CASCADE' },
  maintenance_type: {
    type: 'text',
    notNull: true,
    check: `maintenance_type IN ('オイル交換', 'チェーン清掃・注油', ...)`,
  },
  performed_on: { type: 'date', notNull: true },
  mileage_km: { type: 'integer', notNull: true, check: 'mileage_km >= 0' },
  cost: { type: 'integer' },
  memo: { type: 'text' },
  created_at: { type: 'timestamptz', notNull: true, default: pgm.func('now()') },
});
pgm.createIndex('maintenance_records', ['user_id', 'performed_on']);
```

設計判断のポイント:

- **[ADR-0002](../docs/adr/0002-single-bike-per-user-scope.md)通り、`maintenance_records`は独立した「バイク」エンティティを介さず`user_id`で直接`users`に紐づく**。`sessions`テーブルと同じ`onDelete: 'CASCADE'`パターンを踏襲し、ユーザー削除時に記録も連鎖削除される。
- **整備種別の固定リストをアプリケーション層だけでなくDBのCHECK制約でも強制した**。`users.email`の一意性がDBのUNIQUE制約とアプリのエラーハンドリングの二重で守られているのと同じ考え方で、「自由入力不可」というドメイン不変条件をDBレベルでも保証している。CHECK制約に列挙した8種の文字列は、[CONTEXT.md](../CONTEXT.md)の「整備種別」定義と完全に一致させている。
- **走行距離も`mileage_km >= 0`のCHECK制約で二重に保証**。アプリ層のバリデーション（400エラーを返す）とDB制約（万一アプリ層をすり抜けた場合の最終防衛）の役割分担。
- **`performed_on`（実施日）の未来日禁止だけはDB制約にしていない**。「今日」の判定はサーバーのタイムゾーンに依存する動的な値であり、`CURRENT_DATE`によるCHECK制約は書けなくはないが、リクエスト時点の日付として扱うほうが自然なため、アプリ層のバリデーションのみとした。
- `(user_id, performed_on)`の複合インデックスは、一覧取得のクエリ（`WHERE user_id = $1 ORDER BY performed_on DESC`）を意識した設計。

## APIエンドポイントの実装

新規ファイル[backend/src/routes/maintenanceRecords.ts](../backend/src/routes/maintenanceRecords.ts)を、既存の[backend/src/routes/auth.ts](../backend/src/routes/auth.ts)と同じスタイル（`Router`を返すファクトリ関数、バリデーションをルートハンドラ内にインラインで書く）で実装し、[backend/src/app.ts](../backend/src/app.ts)に`app.use('/maintenance-records', createMaintenanceRecordsRouter())`としてマウントした。

### バリデーションの実装

```ts
if (!MAINTENANCE_TYPES.includes(maintenanceType)) { ... }              // 固定リスト外 → 400
if (typeof performedOn !== 'string' || !/^\d{4}-\d{2}-\d{2}$/.test(performedOn)) { ... }
if (performedOn > today()) { ... }                                     // 未来日 → 400
if (typeof mileageKm !== 'number' || !Number.isInteger(mileageKm) || mileageKm < 0) { ... }
if (cost !== undefined && cost !== null && !Number.isInteger(cost)) { ... }
if (memo !== undefined && memo !== null && typeof memo !== 'string') { ... }
```

`performedOn > today()`は文字列比較だが、両者とも`YYYY-MM-DD`形式に固定しているため、辞書順比較がそのまま日付の大小比較と一致する（ゼロパディングされた同じ桁数の日付文字列は辞書順＝時系列順）。

整備種別の判定に使う固定リストは、マイグレーションのCHECK制約とは別に[backend/src/maintenanceRecords/constants.ts](../backend/src/maintenanceRecords/constants.ts)にTypeScriptの`as const`配列として定義した。

```ts
export const MAINTENANCE_TYPES = ['オイル交換', 'チェーン清掃・注油', ...] as const;
export type MaintenanceType = (typeof MAINTENANCE_TYPES)[number];
```

マイグレーションファイルとこの定数ファイルは値を手動で重複させている。マイグレーションは実行時点のスキーマを記録した歴史的スナップショットという性質上、後から書き換えない前提のファイルであり、アプリケーションコードから動的にインポートする構成にはしなかった（`node-pg-migrate`の実行コンテキストとアプリのビルド成果物は別物であり、依存させると将来のマイグレーション追加時に過去のマイグレーションの意味が変わってしまうリスクがある）。

### レスポンスの命名規則

DBのカラムは`snake_case`（`maintenance_type`、`performed_on`など）だが、JSONレスポンスは`camelCase`（`maintenanceType`、`performedOn`）に変換して返している。

```ts
function toResponseBody(row: MaintenanceRecordRow) {
  return {
    id: row.id,
    maintenanceType: row.maintenance_type,
    performedOn: row.performed_on,
    mileageKm: row.mileage_km,
    cost: row.cost,
    memo: row.memo,
  };
}
```

既存の`/auth`エンドポイントは`{ id, email }`のように単語1つのフィールドしか返しておらず、命名規則を判断する前例がなかった。JavaScript/TypeScriptのAPIレスポンスとしては`camelCase`が一般的であるため、そちらを採用した。

### SQLでの日付の扱い

`performed_on`カラムの型は`date`だが、`pg`ドライバはこれをデフォルトで`Date`オブジェクトに変換して返す。レスポンスは`YYYY-MM-DD`の文字列で統一したいため、クエリ側で`performed_on::text`と明示的にキャストしている。

```sql
SELECT id, maintenance_type, performed_on::text, mileage_km, cost, memo
FROM maintenance_records
WHERE user_id = $1
ORDER BY performed_on DESC, id DESC
```

`ORDER BY`は`performed_on DESC`が主キーだが、同じ実施日の記録が複数あった場合の順序を決定的にするため`id DESC`をタイブレーカーとして追加した。

### 認可

`POST`・`GET`ともに既存の[requireAuth](../backend/src/auth/middleware.ts)ミドルウェアをそのまま利用し、`req.user.id`を所有者として使う。これは[HANDOFF.md](../HANDOFF.md)にissue #3実装時点で明記されていた設計判断（「`requireAuth`は、以降の整備記録関連エンドポイントからもそのままインポートして使う想定」）通り。`GET`は`WHERE user_id = $1`で自分の記録のみに絞り込むため、他ユーザーの記録は原理的に一覧に含まれない。

## テストヘルパーの共通化

[backend/test/integration/auth.test.ts](../backend/test/integration/auth.test.ts)には元々、ファイル内にしか存在しないローカル関数`signupAndLogin`があった。今回の整備記録のテストでも同じ「サインアップしてログインしてトークンを得る」処理が必要になったため、[backend/test/helpers/auth.ts](../backend/test/helpers/auth.ts)に抽出し、両方のテストファイルから使う形にリファクタした。

```ts
export async function signupAndLogin(
  app: ReturnType<typeof createApp>,
  email = DEFAULT_EMAIL,
  password = DEFAULT_PASSWORD,
): Promise<string> { ... }
```

`email`・`password`を引数化したのは、複数ユーザーが必要なテスト（「他ユーザーの記録は一覧に含まれない」）のため。

## resetDbヘルパーの更新

[backend/test/helpers/resetDb.ts](../backend/test/helpers/resetDb.ts)は元々`sessions`と`users`のみをTRUNCATEしていた。新しいテーブルを追加したため、[HANDOFF.md](../HANDOFF.md)に事前に書かれていた通り`maintenance_records`をTRUNCATE対象に追加した。

```ts
await pool.query('TRUNCATE TABLE sessions, users, maintenance_records RESTART IDENTITY CASCADE');
```

## テスト実行順序のハマりどころ: `fileParallelism`

実装が一通り完了した後、`npm test`でファイル単体（`maintenanceRecords.test.ts`のみ）を実行するとテストは全て通るのに、全テストスイート（`auth.test.ts`・`health.test.ts`・`maintenanceRecords.test.ts`の3ファイル）をまとめて実行すると`maintenanceRecords.test.ts`側のGETテストがランダムに401や404で失敗する現象が起きた。

原因はVitestのデフォルト挙動。**Vitestはデフォルトで複数のテストファイルを並列実行する。** 一方この2つのテストファイルはどちらも`beforeEach`で`resetDb()`（実DBに対する`TRUNCATE`）を呼んでいる。ファイルAのテストがユーザーを作成してセッショントークンを使ってリクエストしている最中に、ファイルBの`beforeEach`が`TRUNCATE ... sessions, users`を実行してしまうと、ファイルAが使っていたトークンが消え、直後のリクエストが401になる——という競合状態だった。

これは今回新しく踏んだ問題というより、テストファイルが1つ（`auth.test.ts`）しかなかったissue #3の時点では顕在化していなかった、実DBを共有する統合テストに元々内在していた設計上の課題。今回2ファイル目が同じDBを触るようになって初めて表面化した。

[backend/vitest.config.ts](../backend/vitest.config.ts)に`fileParallelism: false`を追加してテストファイルを直列実行に固定することで解消した。

```ts
export default defineConfig({
  test: {
    globalSetup: './test/globalSetup.ts',
    // Integration tests share one real Postgres instance and call resetDb() in
    // beforeEach; running test files in parallel lets one file's TRUNCATE wipe
    // state another file is mid-assertion on.
    fileParallelism: false,
  },
});
```

修正後、`npm test`を3回連続実行して24件（cost検証追加後は25件）全てが安定してパスすることを確認した。今後さらにテストファイルが増える（issue #5・#6）場合も、実DBを共有し`resetDb()`でTRUNCATEする限りこの設定が必要になり続ける。

## `/code-review`で見つかった指摘と修正

実装完了後、`/code-review`（medium）を実行したところ1件の指摘が出た。

> `cost`のバリデーションが`typeof cost !== 'number'`のみで、小数（`5000.5`）やNaNを弾けていない。`cost`カラムはDB上`integer`型のため、小数を渡すとPostgresの型変換でクエリが例外を投げ、`app.ts`にエラーハンドリングミドルウェアが無いためExpressのデフォルトハンドラが素の500を返してしまう（他のバリデーションエラーは全て400で統一されているのに、ここだけ非対称になる）。

これは実際に妥当な指摘だったため、`typeof cost !== 'number'`を`!Number.isInteger(cost)`に変更し、小数やNaN・Infinityを400で拒否するよう修正した。あわせて`cost: 5000.5`を送るケースの統合テストを追加している。

## 今後のこと

- issue #5（整備記録の編集・削除）は`PATCH /maintenance-records/:id`・`DELETE /maintenance-records/:id`。今回作った`MAINTENANCE_TYPES`定数と、登録時と同じバリデーション（未来日禁止・走行距離0以上）をそのまま再利用できる想定。他ユーザーの記録IDを指定した場合の404/403の実装が新たに必要。
- issue #6（整備種別ごとのサマリービュー）は`GET /maintenance-records/summary`。今回作った`maintenance_records`テーブルに対し、種別ごとに`performed_on`が最新の1件を集計するクエリが必要になる。
- フロントエンドのUI（ログイン画面・整備記録の登録フォーム・一覧画面）は、今回のスコープ判断の通りまだどのissueにも明示的に含まれていない。着手する際は新たなissue化が必要になりそうだが、これは実装者の判断であり次回のセッション開始時にユーザーに確認するのがよい。
