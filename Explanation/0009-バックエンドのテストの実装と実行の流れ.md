# バックエンドのテストの実装と実行の流れ

## 使われている技術

| 役割 | ライブラリ | このプロジェクトでの使われ方 |
|---|---|---|
| テストランナー | [Vitest](https://vitest.dev/) | `describe`/`it`/`expect`/`beforeEach`を提供。[backend/vitest.config.ts](../backend/vitest.config.ts)で設定 |
| HTTPリクエスト発行 | [supertest](https://github.com/ladjs/supertest) | Expressアプリに対してサーバー起動なしで実HTTPリクエストを送る |
| マイグレーション | [node-pg-migrate](https://github.com/salsita/node-pg-migrate) | テスト実行前にテスト用DBへスキーマを適用（[0004](0004-PostgreSQLとマイグレーションの仕組み.md)） |
| 環境変数の切り替え | [dotenv-cli](https://github.com/entropitor/dotenv-cli) | `.env.test`をテスト実行時のみ読み込ませる |

このプロジェクトのテストは「モックでロジックだけ検証する単体テスト」ではなく、**実際のPostgreSQLに対して実際のHTTPリクエストを発行する統合テスト**という方針で統一されている。[backend/test/integration/](../backend/test/integration/)というディレクトリ名がそれを表している。モックを使わない理由は、Expressのルーティング・バリデーション・SQL・DB制約（UNIQUE制約など）が組み合わさって初めて正しさが保証される処理が多く、個々をモックで切り離すとその結合部分のバグを検出できないため。

## 実行の流れ（コマンド1つでも中では何段階も起きている）

[README.md](../README.md)に書かれている通り、実行コマンドは2つだけ。

```sh
docker compose up -d postgres-test   # ① テスト専用DBコンテナを起動
cd backend && npm test               # ② テスト実行
```

`npm test`の中身は[backend/package.json](../backend/package.json)でこう定義されている。

```json
"test": "dotenv -e .env.test -- vitest run"
```

この1行で実際には次の順番で処理が進む。

1. **`dotenv -e .env.test`** が [backend/.env.test](../backend/.env.test) を読み込み、`DATABASE_URL`を`postgres://bike_maintenance:bike_maintenance@localhost:5433/bike_maintenance_test`（ポート5433 = `docker-compose.yml`の`postgres-test`）に設定した状態で`vitest run`を起動する。開発用DB（`.env`、ポート5432）とは完全に別のDBに向くため、テストで開発中のデータを壊す心配がない。
2. **Vitestの`globalSetup`**（[backend/vitest.config.ts](../backend/vitest.config.ts)で指定された[backend/test/globalSetup.ts](../backend/test/globalSetup.ts)）が、テストファイルを実行する前に一度だけ`node-pg-migrate`の`runner()`を呼び、テスト用DBへ未適用のマイグレーションをすべて適用する。`globalSetup`はVitestの仕組みで「全テストファイルを通して1回だけ」実行される特別なフックであり、各テストファイルの`beforeEach`とは実行タイミングが異なる。
3. マイグレーションが完了した状態のDBに対して、`test/integration/`配下の各`*.test.ts`が実行される。

## 実際のテストコードで何をしているか

### [health.test.ts](../backend/test/integration/health.test.ts) — 一番単純な例

```ts
const app = createApp();
const response = await request(app).get('/health');
expect(response.status).toBe(200);
expect(response.body).toEqual({ status: 'ok', database: 'connected' });
```

[backend/src/app.ts](../backend/src/app.ts)の`createApp()`はExpressの`app`インスタンスを返す関数（ファクトリ関数）になっている。ポイントは`app.listen()`でポートを開いていないこと。supertestは`app`オブジェクトを直接受け取り、内部で一時的なソケットを使ってHTTPリクエストをシミュレートするため、実際にポートを待ち受けなくてもHTTPレベルのテストができる。

`/health`エンドポイント自体（[app.ts:10-17](../backend/src/app.ts)）は`pool.query('SELECT 1')`でDB接続を確認しているだけなので、このテストが通ることは「Expressのルーティング」と「DBに実際に接続できること」の両方を同時に検証している。

### [auth.test.ts](../backend/test/integration/auth.test.ts) — DBの状態を扱うテスト

こちらはユーザーの登録状態がテスト間で影響し合う可能性があるため、`describe`ブロックごとに次のパターンが繰り返されている。

```ts
describe('POST /auth/signup', () => {
  beforeEach(async () => {
    await resetDb();
  });
  // ...
});
```

[backend/test/helpers/resetDb.ts](../backend/test/helpers/resetDb.ts)の中身は1行。

```ts
await pool.query('TRUNCATE TABLE sessions, users RESTART IDENTITY CASCADE');
```

- `TRUNCATE ... RESTART IDENTITY`: `users`テーブルの自動採番（`id`）を1から振り直す。これがないと、あるテストで作成したユーザーの`id`が前のテストの実行順に依存してしまい、`expect(response.body).toEqual({ id: expect.any(Number), ... })`のように緩く検証せざるを得なくなったり、テストの実行順が変わると結果が変わる不安定なテストになる。
- `CASCADE`: `sessions`テーブルは`users.id`を外部キー参照しているため、`users`だけをTRUNCATEすると外部キー制約でエラーになる。`sessions, users`と両方指定し`CASCADE`を付けることで、依存関係を含めて一括で空にしている。
- `beforeEach`（`beforeAll`ではない）: 「各テストの前に必ず空の状態から始める」ことで、テストの実行順序に関係なく同じ結果になることを保証している。例えば「409を返す」ためのテスト（[auth.test.ts:42-53](../backend/test/integration/auth.test.ts)）は、直前で同じメールアドレスをsignupさせてから重複signupを試みる構成になっているが、これは`resetDb()`で毎回まっさらな状態から始まる前提で書かれている。

`GET /auth/me`や`POST /auth/logout`のテストでは、ヘルパー関数`signupAndLogin`（[auth.test.ts:6-14](../backend/test/integration/auth.test.ts)）でsignup→loginを1回にまとめ、実際のセッショントークンを取得してから本題のテストに進んでいる。これは「認証が必要なエンドポイントのテスト」には必ず有効なトークンが要る、という[backend/src/routes/auth.ts](../backend/src/routes/auth.ts)の`requireAuth`ミドルウェアの仕様を反映した準備コード。

logoutのテスト（[auth.test.ts:136-147](../backend/test/integration/auth.test.ts)）は「ログアウトが本当にセッションを無効化しているか」を、logout自体のレスポンス（204）だけでなく、その後に同じトークンで`/auth/me`を呼んで401が返ることまで確認している。これはDBの`sessions`テーブルから該当行が削除されたことを、間接的にHTTPレスポンスの変化として検証しているということでもある。

## なぜこの構成なのか（backendアーキテクチャとの接続）

- `pool`（[backend/src/db.ts](../backend/src/db.ts)）はアプリ全体で1つのシングルトンとしてモジュールレベルでエクスポートされている。テストコードもプロダクションコードも同じ`pool`を使うため、テスト用DBに向いた`DATABASE_URL`さえ環境変数で与えれば、コード自体は一切変更せずにテスト用DBに対して動作する。
- `createApp()`がファクトリ関数になっているのは、各テストで新しい`app`インスタンドを作れるようにするため（副作用のあるミドルウェア登録などをテストごとにやり直せる）。ただし`pool`自体は共有されたままなので、DBの状態のクリーンアップは`resetDb()`が担っている。

この構成により、「`docker compose up -d postgres-test && npm test`を実行すれば、マイグレーション適用からDBクリーンアップ、HTTPレベルの検証まで全部自動でやってくれる」という、[0005](0005-マイグレーションにDBコンテナの起動が必要な理由.md)で触れた「コンテナ起動だけは人間がやる、それ以外は自動」という設計が実現されている。
