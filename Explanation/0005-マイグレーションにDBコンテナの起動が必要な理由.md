# マイグレーションにDBコンテナの起動が必要な理由

## マイグレーションツールは「ただのDBクライアント」

[node-pg-migrate](https://github.com/salsita/node-pg-migrate)自体はDBを起動したり管理したりする仕組みを持っていない。[backend/src/db.ts](../backend/src/db.ts)が`pg`の`Pool`で`DATABASE_URL`にTCP接続しているのとまったく同じ立場で、node-pg-migrateも`DATABASE_URL`（例: `postgres://bike_maintenance:bike_maintenance@localhost:5432/bike_maintenance_dev`、[backend/.env.example](../backend/.env.example)参照）へ普通にTCP接続してSQLを発行しているだけの「クライアント」でしかない。

したがって、接続先の`localhost:5432`（開発用）や`localhost:5433`（テスト用）で実際にPostgreSQLプロセスが待ち受けていなければ、マイグレーションどころか最初の接続確立の時点で`ECONNREFUSED`になる。これは`db.ts`経由でアプリ本体が接続に失敗するのとまったく同じ理由・同じ失敗の仕方。

## 起動順序（このプロジェクトでの実際の手順）

[README.md](../README.md)に明記されている通り、常に「コンテナ起動 → マイグレーション」の順を守る必要がある。

```sh
docker compose up -d          # ① DBコンテナ(postgres, postgres-test)を起動
cd backend && npm run migrate # ② 起動後に開発用DBへマイグレーション適用
```

テスト用DBも同様。

```sh
docker compose up -d postgres-test
cd backend && npm test
```

## 「自動で流れる」のはマイグレーション実行そのものだけ

[backend/test/globalSetup.ts](../backend/test/globalSetup.ts)は`npm test`実行時に毎回自動でマイグレーションを適用してくれる（[0004](0004-PostgreSQLとマイグレーションの仕組み.md)参照）。ただしこれは「マイグレーションの実行し忘れを防ぐ」自動化であって、「コンテナそのものを起動する」自動化ではない。`postgres-test`コンテナが起動していない状態で`npm test`を叩くと、globalSetupの中の`runner()`呼び出しがDB接続に失敗してテストが即座にエラーで落ちる。コンテナの起動だけは人間が（またはCIの設定が）事前に済ませておく必要がある。
