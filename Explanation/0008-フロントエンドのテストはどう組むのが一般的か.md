# フロントエンドのテストはどう組むのが一般的か

## このプロジェクトの現状: backendだけにテストがある非対称な状態

[backend/package.json](../backend/package.json)には`test`/`test:watch`スクリプトがあり、[backend/test/integration/](../backend/test/integration/)にVitest + supertestによる統合テスト（`auth.test.ts`、`health.test.ts`）が存在する。実際のPostgreSQL（テスト用コンテナ）に対してAPIを叩き、DBの状態まで含めて検証する構成（[0004](0004-PostgreSQLとマイグレーションの仕組み.md)参照）。

一方[frontend/package.json](../frontend/package.json)の`scripts`は`dev`/`build`/`lint`/`preview`のみで、テストスクリプトがない。`devDependencies`にもVitestやTesting Libraryの類が一切入っていない。つまりfrontendは現時点で「テストが薄い」のではなく「テストの仕組みそのものが存在しない」状態。これは手抜きというより、[frontend/src/App.tsx](../frontend/src/App.tsx)がまだ`/health`の疎通確認しか行っていない、開発の初期段階だからだと考えられる。

## フロントエンドテストの3層構造

Reactアプリのテストは、検証したい対象の粒度によって役割が分かれる。

### 1. コンポーネント（単体）テスト — Vitest + React Testing Library

個々のコンポーネントを実ブラウザなしで仮想DOM（jsdom）上にレンダリングし、propsや状態に応じた表示・イベントハンドラの呼び出しを検証する。例えば「バリデーションエラー時にメッセージが表示される」「送信ボタンを押すとonSubmitが呼ばれる」といった、コンポーネント単体で閉じたロジックの確認に向く。

backendが既にVitestを採用しているため（[backend/package.json](../backend/package.json)の`vitest`）、frontendでも同じランナーを使うのが最も自然な選択になる。Viteプロジェクトなので設定の親和性も高く、`vitest.config.ts`に`environment: 'jsdom'`を指定し、`@testing-library/react`を追加する程度で始められる。backendの統合テストのように実DBへ接続する必要がなく、外部依存（`fetch`など）はモックして高速に回すのが基本。

### 2. E2E（End-to-End）テスト — Playwright / Cypress

実際のブラウザを起動し、frontendとbackendを両方本当に立ち上げた状態でユーザー操作をシミュレートする。「サインアップフォームに入力して送信すると、ログイン済み状態の画面に遷移する」のような、複数コンポーネント・複数画面・実際のAPI呼び出しをまたぐシナリオの検証に向く。

直近のコミット45bf7ad「サインアップ・ログイン・ログアウトの認証フローを実装」はbackend側のAPIとして実装されたものだが、これをfrontendのUIから使う画面ができた時点で、こうしたE2Eテストの対象になる。backendの[auth.test.ts](../backend/test/integration/auth.test.ts)がAPIレベルで検証している「サインアップ→ログイン→ログアウト」の一連の流れを、今度はブラウザ操作レベルで再現するイメージ。

### 3. 静的検証（テストの前段）

型チェック（`tsc -b`、[frontend/package.json](../frontend/package.json)の`build`スクリプトに含まれる）とlint（`oxlint`）は、テストを書く前から得られる最低限の正しさの担保になる。特にTypeScriptの型チェックは「propsの型が合っていない」「未定義の可能性がある値を扱っている」といったクラスのバグを、テストコードを書かずに検出できる。

## まとめ: このプロジェクトでの今後の流れ

frontendに認証UI（サインアップ/ログイン/ログアウトの画面）を実装する段階になったら、

1. フォームや状態表示のコンポーネント単体を Vitest + React Testing Library でテスト
2. 実際の画面遷移とAPI連携を Playwright でE2Eテスト

という2段構えを、backendの統合テストに追加する形で整備していくのが一般的な流れになる。
